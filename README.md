# Anime Recommender

A content-based recommendation engine for anime, built with scikit-learn and Streamlit.
Type in a title you like, get similar ones back — ranked by textual and semantic similarity.

## Overview

This project recommends anime **without using any user data**. Instead of collaborative
filtering ("people who liked X also liked Y"), it compares the *content* of each title —
its name and genres — and returns the closest matches.

That design choice has a concrete advantage: there is no cold-start problem. A brand-new
anime with zero ratings can still be recommended the moment it enters the catalogue,
because its genres alone are enough to place it in the similarity space.

The app ships with two interchangeable models so their behaviour can be compared
side by side on the same query.

---

## Features

- Two recommendation models behind a single interface, switchable at runtime
- Semantic matching over 15k plot summaries, not just genre tags
- Search by original title **or** English title — `Attack on Titan` resolves to `Shingeki no Kyojin`
- Typo tolerance via approximate string matching — `one pece` suggests `One Piece`
- Filter recommendations by format (TV, Movie, OVA, Special, ONA, Music)
- Reproducible cleaning pipeline from the raw Kaggle export
- Sub-10 ms queries on a 17k-title catalogue

---

## How it works

Both models share the same pipeline: build one text document per anime, embed every
document into a vector space, then rank the catalogue by cosine similarity to the query
title. They differ only in how that vector is produced.

### TF-IDF (default)

Each anime becomes a bag of weighted words. Terms that appear everywhere (`action`)
are down-weighted; rare, discriminative terms carry more signal. Similarity is the
cosine of the angle between two sparse vectors.

Fast, fully deterministic, and easy to explain — you can point at the exact shared
tokens that caused a recommendation. Vocabulary size on the current dataset: **15,477 terms**.

### Sentence embeddings (optional)

Uses `all-MiniLM-L6-v2` from `sentence-transformers` to map each document to a dense
384-dimensional vector. Vectors are L2-normalised at encoding time, so cosine similarity
reduces to a plain dot product.

Embeddings are computed once and cached to disk as `.npy`, keyed by a hash of the corpus
and model name — change the data and the cache invalidates itself automatically.

> **Why this matters here:** TF-IDF matches *strings*, not meaning. Ask it for titles
> similar to `Death Note` and it returns `Nissan Note x The World of Golden Eggs` — a car
> commercial — because both contain the token `Note`. The embedding model reads the
> summaries and never makes that mistake. That gap is the whole argument for the second
> model, and it only exists because the corpus contains real prose.
>
> The cost is real too: `sentence-transformers` pulls in roughly 1 GB of PyTorch, and the
> first run downloads ~90 MB of model weights. TF-IDF remains the default for that reason.

### Ranking

Similarity is computed **one row against the catalogue**, never as a full N×N matrix.
The pairwise matrix for 17k titles would occupy 2.5 GB in `float64` and exceed the memory
limit of most free hosting tiers; the row-wise version needs a few kilobytes.
Top-*k* selection uses `np.argpartition` (O(n)) rather than a full sort.

## Project structure

```
anime-recommender/
├── app.py                 # Streamlit interface
├── prepare_data.py        # Raw Kaggle CSV → cleaned dataset
├── requirements.txt
├── src/
│   ├── __init__.py
│   └── recommender.py          # BaseRecommender + TF-IDF and embedding models
└── data/
    ├── anime.csv               # Raw dataset
    ├── anime_with_synopsis.csv # Plot summaries
    ├── anime_clean.csv         # Generated by prepare_data.py
    └── cache/                  # Cached embeddings (gitignored)
```

`recommender.py` follows the **template method** pattern: `BaseRecommender` owns data
loading, title lookup, filtering and ranking, while each subclass implements a single
method, `_similarities(idx)`. Adding a third model means writing that one method — the
rest is inherited.

## Getting started

### 1. Install

```bash
git clone https://github.com/aissouss/anime-recommender.git
cd anime-recommender
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

To skip the ~1 GB PyTorch download, comment out `sentence-transformers` in
`requirements.txt`. The app detects the missing dependency and disables that model
cleanly instead of crashing.

### 2. Get the data

Already included in `data/`. To rebuild it from scratch, download **[Anime Recommendation Database 2020](https://www.kaggle.com/datasets/hernan4444/anime-recommendation-database-2020)**
from Kaggle and place `anime.csv` in `data/`.

### 3. Build the clean dataset (optional — already committed)

```bash
python prepare_data.py
```

```
data/anime_clean.csv generated: 17495 rows kept out of 17562.
  - missing ratings : 5090
  - types           : ['Movie', 'Music', 'ONA', 'OVA', 'Special', 'TV', 'Unknown']
```

### 4. Run

```bash
streamlit run app.py
```

Open http://localhost:8501.

## Dataset

Source: *Anime Recommendation Database 2020* (Hernan Valdivieso, Kaggle) — scraped
from MyAnimeList.

Two files from that dataset are used and both are committed, so the project runs
immediately after cloning, without a Kaggle account:

- `anime.csv` — one row per anime: title, genres, format, score
- `anime_with_synopsis.csv` — plot summaries, joined on `MAL_ID`

`prepare_data.py` merges them into `anime_clean.csv`. The synopsis file is optional:
if it is absent the pipeline still runs and warns that the semantic model will be
operating blind.

After cleaning:

| | |
|---|---|
| Titles | 17,495 |
| With a synopsis | 15,451 (88%) |
| Mean synopsis length | 383 characters |
| With an English title | 5,624 |
| Without a score | 5,090 |
| Formats | TV (4,988) · OVA (3,889) · Movie (2,995) · Special (2,218) · ONA (1,900) · Music (1,469) |

Four cleaning details are worth flagging, because each one silently degrades a naive
pipeline:

- Missing values are stored as the **string** `"Unknown"`, not as `NaN`. `fillna()` does
  not catch them, and the score column stays typed as text — any later `float()` call
  raises `ValueError`. The fix is `pd.to_numeric(..., errors="coerce")`.
- Some entries repeat the original title in the English column. Those are blanked out
  so the search index does not carry duplicate keys.
- 745 entries carry the placeholder *"No synopsis information has been added…"*. Left in,
  those 745 identical strings would make completely unrelated shows look near-identical
  to each other. They are replaced with an empty string.
- The synopsis column is misspelled `sypnopsis` in the source file, and roughly half the
  summaries end in a credit line such as `(Source: ANN)`. Both are handled at load time.

## Performance

Measured on the full 17,495-title catalogue, TF-IDF model:

| Metric | TF-IDF |
|---|---|
| Index build | ~3 s |
| Peak memory | ~25 MB |
| Query latency | ~14 ms |
| Sparse matrix | 17,495 × 50,000 (562,970 non-zero) |

The embedding model is heavier: the first run downloads ~90 MB of weights and encodes the
whole catalogue (a few minutes on CPU). The result is written to `data/cache/*.npy`, so
every subsequent start is instant. The cache key is a hash of the corpus plus the model
name, so editing the data invalidates it automatically.

The Streamlit app wraps model construction in `@st.cache_resource`, so the index is
built once per process and reused across reruns.

## Limitations

- **No evaluation metric yet.** Recommendation quality is currently assessed by
  inspection only. There is no held-out set and no precision@k figure, so claims of
  quality should be read as qualitative.
- **12% of titles have no synopsis.** For those, the semantic model falls back to
  title and genres alone and behaves roughly like TF-IDF.
- **Summaries describe plot, not tone.** Two shows with a similar premise can differ
  wildly in register — a parody and the work it parodies read almost the same.
- **No popularity prior.** Obscure titles with a near-identical genre string can outrank
  well-known ones. The dataset has `Members` and `Popularity` columns that could
  temper this.
- **No personalisation.** The system knows nothing about *you* — only about the one
  title you typed.
